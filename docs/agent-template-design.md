# Agent 审批与事件处理模板构想

方案草案。现有校园项目作为首个试点，保留其申请、审批、预约和统计等业务模块。

## 模板提供的能力

| 可复用部分 | 职责 | 社团场景中的实例 |
|---|---|---|
| 工单和事件 | 接收申请、变更和定时触发，关联处理对象与来源 | 活动申请提交、场地征用、活动即将开始 |
| 规则与授权 | 按事项配置必填资料、执行条件、操作范围和人工审批条件 | 原时段内等条件换场可自动执行，改期进入人工审批 |
| 任务处理 | 读取当前数据，产生可校验的方案，调用已授权的业务动作 | 查受影响预约、筛选场地、批量更新预约、通知报名学生 |
| 跟进与记录 | 持久化任务、处理结果、异常、通知和接管记录 | 查看受影响活动、改场原因及通知状态，等待空位后重试 |

新业务提供自己的申请表单、角色、规则和读写接口。模板负责接收事件、按规则推进工单和记录结果。可以先在同一校园场景验证第二类业务，如设备借用，避免让通用流程依赖场地的专用字段。

## 可在现有系统验证的三个场景

1. **申报补全与审批分流。** 提交后检查资料、场地需求和审批冲突。信息缺失时说明缺少哪些字段并提醒申请人。符合已授权条件的低风险事项可以直接进入下一步，其余按规则交给对应审批人。
2. **征用后自动换场。** 校方登记征用后，触发处理任务。读取预约，复用容量、设备、时间与批量匹配规则。允许自动执行时，在写入前复验冲突，更新预约和处理记录，再通知负责人及有效报名学生。确实无合适场地时保留待协调状态并提醒负责人。
3. **按状态发送提醒。** 审批超时提醒当前审批人，活动开始前按最新有效预约提醒参与者，征用后的通知包含旧场地、新场地和原定时间。活动已取消或换场后，先复查业务状态，再执行尚未发送的提醒。

DeepSeek 可以把征用通知或自由文本申请整理成结构化字段，提供补充说明和通知措辞。场地选择、审批授权和写入条件使用确定性校验。结构化事件可由规则直接处理。

## 首个迭代

建议先做「登记征用 → 自动换场 → 站内通知 → 处理记录」这一闭环。把预授权范围、审批方式和执行动作放到场景配置。可同时从旧流程进入人工处理，以及从事件入口按预授权自动处理。

任务带事件编号。重复的征用事件应复用已有结果，重复处理和重启恢复时应避免新增相同预约或通知。预约和待发送通知在同一数据库事务中记录，发送任务读取已提交记录后再处理。执行记录展示触发来源、规则版本、输入条件、预约前后值和通知结果。

验收时使用已有的两场活动。如果候选满足要求，两场按原时段换场，相关账号在消息页看到新场地。如果只有一间合适场地，匹配可以成功的一场，另一场进入待协调。补验重复事件、写入前候选被占用和送达失败后重试。流程通过后，用设备借用验证能否只新增表单、规则和业务适配代码。
